# T0 0.1 到 0.2 的设计审查

日期：2026-10-27。范围：协议、Schema、固定向量与证据规则的静态审查。
状态：`READY_FOR_HUMAN_DESIGN_REVIEW`，尚未接受或授权实现。

## 已确认的问题与修订

| 0.1 缺口 | 已确认依据 | 0.2 处理 |
|---|---|---|
| 相同 domain 的具体来源及受信控制上下文不够明确 | 同为 HOST_STEADY 不保证同一来源；全部字段来自另一 host 也可能内部自洽 | 运行上下文独立于动作 payload；核对登记来源、metadata 和当前控制 clock |
| 未独立覆盖同源 SYSTEM_TIME | 只检查 domain 是否彼此相等，会漏掉所有字段都用 wall clock 的情况 | 首轮只允许 HOST_STEADY；新增 T0-19 |
| 部分来源/session 反例同时数值到期 | 原跨域/session 向量 now=120 ms、expiry=100 ms | 改为 now=80 ms；默认观测预算 1000 ms，将故障因素分开 |
| 计划使用的 Python 校验器对末尾换行过宽 | 用已有 jsonschema 4.26.0 检查 timestamp=`80000000\n`，0.1 返回合法；Node.js 的旧正则探针则拒绝，结果不能跨引擎推定 | 0.2 改成严格字符串结尾断言；T0-33 在两种引擎的静态探针中均拒绝 |
| 非法时间顺序、测量点与未知同步状态的覆盖不足 | 0.1 虽有原则描述，缺少相应固定反例 | 新增 T0-20…27、T0-30 等固定输入 |
| 证据完整性可误依赖自报标志 | 0.1 使用 evidence_complete 和 missing 列表，不足以约束复核机制 | 改为实际字段形状的合成证据输入，并核对进展、sink 计数、丢失和序号连续性 |
| 没有“确实输出了命令”的反证 | 零日志和不完整证据不能区分真实输出行为失败 | T0-31 给出完整的一条 sink 输出，预期明确 FAIL |
| 设计冻结与实现 hash 混在同一门槛 | 没有实现授权时不能先产生实现 hash | 分开设计接受/本地实现授权与正式运行快照冻结；支持明确的一次条件式正式运行授权 |

这些是设计审查发现，不是已有 Runtime 发生过的故障；不得将修订写成已验证的运行修复。
原 0.1、SIG-A0 接受记录、Notion 投影及原哈希清单保持原样。本版不改变已接受架构、上游处置或现有授权范围。
